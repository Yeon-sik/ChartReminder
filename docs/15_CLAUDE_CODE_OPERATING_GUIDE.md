# Claude Code 운영 가이드

## 1. 한 세션에 한 목표

좋은 요청:

> M3 리플레이 상태 머신만 구현하고 관련 테스트와 문서를 갱신해.

나쁜 요청:

> 앱 전체를 완성하고 예쁘게 만들어.

## 2. 먼저 계획, 그다음 구현

새 마일스톤 시작 시 Claude에게 다음을 요구한다.

1. 관련 문서 읽기
2. 기존 코드 조사
3. 요구사항과 코드 충돌 확인
4. 구현 계획 제시
5. 승인된 범위만 수정

단, 이미 마일스톤 프롬프트가 충분히 구체적이라면 Claude가 불필요한 재질문으로 멈추지 말고 합리적인 기본값과 명시적 가정으로 진행하게 한다.

## 3. Context 관리

- `CLAUDE.md`는 짧은 불변 규칙만 유지
- 긴 세부 명세는 필요할 때만 읽게 함
- 끝난 세션의 장황한 대화를 이어가기보다 `PROJECT_STATE.md`를 갱신하고 새 세션 시작
- `/usage`, `/context`, `/mcp` 등 현재 Claude Code가 제공하는 명령으로 사용량과 연결 상태 확인
- 사용하지 않는 MCP는 연결 해제 또는 비활성화

## 4. MCP 사용 원칙

Playwright는 UI를 실제로 확인해야 할 때만 사용한다.

- 매 사소한 코드 변경마다 브라우저를 열지 않음
- M5 UI 검증부터 적극 사용
- 한 번의 브라우저 세션에서 관련 시나리오를 묶어 확인
- 긴 DOM·콘솔·스크린샷 결과를 불필요하게 반복 수집하지 않음

## 5. Skill 사용 원칙

- `feature-dev`: 기능 경계가 명확한 마일스톤에 사용
- `frontend-design`: M5 이후
- Context7 또는 공식 문서 도구: 라이브러리 API 확인
- TypeScript/Rust LSP: 정의·참조·진단
- 보안 검토: 인증정보, 파일 권한, 배포 단계

## 6. Claude의 완료 보고를 그대로 믿지 않기

다음을 직접 확인한다.

- 실제 명령 로그
- Git diff
- 테스트 개수와 실패 여부
- 앱 실행
- 스크린샷
- PROJECT_STATE

“완료했습니다”는 증거가 아니라 주장이다.

## 7. 작업 중단 기준

Claude는 다음 상황에서 구현을 확대하지 말고 명확히 보고해야 한다.

- 데이터 공급자 이용조건 불명확
- 문서 간 중대한 충돌
- 기존 사용자 변경과 충돌
- 비밀정보가 필요한데 안전한 입력 경로가 없음
- 실패 테스트를 해결하려면 요구사항 변경이 필요
